# 0003. 익명 식별키로 사용자를 구분하고 로그인 화면을 만들지 않는다

상태: 확정 · 서버 검증은 인증서 확보 전까지 보류 · 2026-09-03

## 배경

가계부는 사용자별 데이터가 필요하다. 그런데 제품 원칙 1번이 "첫 기록 전 필수 질문 0개" 다.
로그인 화면은 그 자체로 이탈 지점이고, 가계부를 세 번 포기한 사람에게 네 번째 포기 사유를 주는 일이다.

## 결정

`User.getAnonymousKey()` 가 돌려주는 해시를 사용자 키로 쓴다. 로그인 화면도 토스 로그인 연동도 MVP 에 넣지 않는다.
프론트는 그 해시를 `X-Anon-Key` 헤더에 실어 보내고, 백엔드가 그 값으로 사용자 행을 찾거나 만든다.

## 근거

- 동의 화면 없이 즉시 얻는다. 토스 앱 5.232.0 이상에서 쓸 수 있고 `User.getAnonymousKey.isSupported()` 로 미리 확인한다.
- 미니앱별로 다른 해시라 우리 앱 밖으로 사용자를 식별할 수 없다. 개인정보를 덜 갖는 쪽이 안전하다.
- 기기가 아니라 토스 계정에 붙는 값이라, 기기를 바꿔도 데이터가 따라온다.

## 대안

- **토스 로그인**: 실명과 연락처를 얻지만 동의 화면이 생긴다. 원칙 1번과 정면으로 충돌한다.
- **기기 로컬 저장소에 UUID 발급**: 서버 왕복이 없어 가장 빠르지만 앱을 지우면 데이터가 사라진다. 가계부에서는 치명적이다.

## 결과

- 클라이언트는 브릿지의 `getIdentity()` 만 안다. `User.getAnonymousKey` 를 화면에서 직접 부르지 않는다.
- 미지원 버전이면 `BridgeError('UNSUPPORTED')` 가 나온다. 화면은 이 경우를 반드시 처리한다.
- **서버 검증은 아직 못 한다.** 공식 검증 API 는 `POST https://apps-in-toss-api.toss.im/api-partner/v1/apps-in-toss/users/anon-key/verify` 이고 **mTLS 클라이언트 인증서가 필요한데 우리는 인증서를 아직 갖고 있지 않다.** 가짜 인증서를 만들지 않는다.
- 그래서 검증기를 인터페이스로 둔다.
  - `AnonKeyVerifier` : 계약
  - `TossAnonKeyVerifier` : mTLS 실제 호출. 인증서가 생기면 설정만 바꿔 켠다
  - `TrustingAnonKeyVerifier` : 로컬 개발용. 검증 없이 통과시키고, **운영 환경에서 켜지면 기동을 실패시킨다**
- 이 API 는 비즈니스 오류를 `HTTP 200 + resultType:"FAIL"` 로 준다. 상태코드만 보고 성공으로 판정하면 안 된다. `errorCode` 4010 은 인증 정보 없음, 4095 는 요청 한도 초과(앱당 분당 3,000회)다.
- 인증서를 받으면 이 ADR 의 상태를 갱신한다.
