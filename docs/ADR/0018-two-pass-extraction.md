# 0018. 사진은 다듬어 보내고, 싼 모델로 먼저 읽은 뒤 서버 검증에 걸린 것만 비싼 모델로 다시 읽는다

상태: 확정 · **사용자가 구조를 그려 정했다** · 2026-09-11

## 배경

ADR-0016 이 Gemini 를 기본으로 두고 값은 "결정 요인이 아니다" 라고 적었다. 그때 근거로 쓴
숫자가 세로 캡처 한 장에 약 $0.0014 였는데, 그 뒤 두 가지가 바뀌었다.

- `gemini-2.5-flash` 가 새 키에서 내려갔다. 후속인 3.6 Flash 는 **$0.75 / $3.75** 이고
  **2027-01-01 에 두 배**가 된다. 한 장에 약 $0.0031, 1월부터 약 $0.0061 이다.
- 예비로 둔 `gpt-5-mini` 는 **2026-12-11 에 종료**된다.

값을 다시 재 보니 이미지·strict 스키마를 다 하면서 가장 싼 현행 모델이 **gpt-5.6-luna**
($0.20 / $1.20)였다. 3.6 Flash 대비 입력 3.75배 · 출력 3.1배 싸고 1월 인상도 없다.

그런데 루나는 nano 급 후속이다. 영수증을 잘 읽는지 재 본 적이 없다. **싼 모델 하나로 갈아타는
것은 값을 아끼는 대신 인식 품질을 도박에 거는 일이다.**

사용자가 구조를 그려 정했다.

```
사진 → 전처리 → Luna → 서버 검증 → 정상이면 자동 등록
                          ↓ 이상
                   Terra / Flash-Lite 재시도
                          ↓ 그래도 이상
                     사용자에게 확인
```

그리고 한 줄을 덧붙였다: **"Terra로 가는 것은 최소화해."**

## 결정

1. **보내기 전에 사진을 다듬는다**(`integrations/imaging.py`). EXIF 회전을 적용하고,
   단색 테두리를 잘라내고, 긴 변을 1600px 로 줄인다. **메타데이터를 통째로 버린다.**
2. **1차는 늘 싼 모델이다.** provider 기본값을 `gpt-5.6-luna` 로 올린다(옛 `gpt-5-mini` 는 종료).
3. **서버가 결과를 한 번 본다**(`domain/extraction_review.py`). 순수 함수다.
   미래 날짜 · 너무 오래된 날짜 · 상한을 넘는 금액 · 낮은 확신 · 한 결과 안의 같은 결제 중복 ·
   한 건도 못 읽음.
4. **걸린 것만 재시도한다.** 재시도 모델은 `LLM_ESCALATION_MODEL`(기본 `gpt-5.6-terra`,
   Gemini 면 `gemini-3.5-flash-lite`). **1차가 깨끗하면 두 번째 모델은 아예 안 뜬다.**
5. **재시도 지시에 무엇이 이상했는지 적어 보낸다.** 같은 지시를 그대로 주면 같은 답이 또 온다.
6. **세 번째는 없다.** 다시 읽어도 이상하면 그 후보의 선택을 꺼서 사람에게 넘긴다.
7. **어느 모델이 읽었고 재시도까지 갔는지 남긴다**(`parse_usages.model`·`escalated`).

## 근거

- **전처리를 넣은 이유.** 셋 다 값과 정확도에 바로 닿는다. 누운 영수증은 잘 안 읽히고,
  캡처의 단색 여백은 그만큼이 이미지 토큰으로 계산되며, 긴 변 상한이 값을 가장 크게 가른다.
  덤으로 **영수증 사진의 GPS 좌표가 여기서 끊긴다.** ADR-0010 이 "이미지 안의 카드번호는
  가릴 수단이 없다" 고 적었는데, 위치 정보만큼은 가릴 수단이 생겼다.
- **두 모델로 나눈 이유.** 싼 모델 하나면 값은 최선이지만 틀린 값이 조용히 남는다. 비싼 모델
  하나면 품질은 최선이지만 열 배를 매번 낸다. **틀릴 때만 비싼 값을 내는 것**이 두 축을 다 잡는다.
- **검증을 순수 함수로 둔 이유.** DB 도 세션도 모르게 두면 규칙을 테스트로 못 박을 수 있고,
  "무엇이 이상한가" 와 "그래서 어떻게 할까" 가 섞이지 않는다.
- **의심스러우면 이상으로 본 이유.** 잘못 통과시키면 틀린 금액이 가계부에 남는다. 잘못 막으면
  사람이 한 번 더 볼 뿐이다. 값이 대칭이 아니다.
- **재시도 실패를 무시하는 이유.** 1차 답이 있는데 두 번째 호출이 죽었다고 사용자에게
  아무것도 못 준다고 하는 것은 과하다. 그때는 1차 결과를 사람 확인으로 넘긴다.
- **DB 에 모델 이름을 남기는 이유.** luna 와 terra 가 둘 다 `openai` 라 provider 만으로는
  안 갈린다. **「Terra 로 가는 것은 최소화해」 를 지키고 있는지 세려면 이 두 컬럼이 있어야 한다.**

## 대안

- **모델 하나로 간다(루나만).** 버렸다. 인식 품질을 재 본 적이 없어 그대로 갈아타면 도박이다.
- **모델 하나로 간다(테라만).** 버렸다. 매 장 열 배다. 대부분의 캡처는 루나로 충분하다.
- **재시도를 두 번(테라 → 플래시라이트) 한다.** 버렸다. 두 모델이 다 이상하다고 한 입력은
  사진 자체가 흐리거나 우리 프롬프트가 안 맞는 것이다. 세 번째를 부를 값으로 사람이 본다.
- **검증에 걸린 후보만 재시도한다(부분 재시도).** 버렸다. 사진 한 장을 반만 다시 읽을 수 없다.
  줄글은 가능하지만 두 경로가 갈라지고, 이득이 값 몇 푼이다.
- **검증에 걸리면 바로 사용자 확인으로 보낸다(재시도 없음).** `LLM_ESCALATION_MODEL` 을 비우면
  이 동작이다. 기본으로 두지 않았다. 확인 창이 잦으면 "10초" 라는 약속이 깨진다.
- **자동 등록을 검토 화면 없이 바로 저장으로 만든다.** 버렸다. 사용자가 그린 그림의 "자동등록"
  은 **후보가 켜진 채로 내려온다**는 뜻으로 읽었다. 검토 화면을 없애면 잘못 읽은 것을 되돌릴
  자리가 사라진다. 지금도 확신 높은 후보는 켜진 채 내려오고 저장은 한 번이다.
- **전처리를 클라이언트에서 한다.** 버렸다. 기기마다 결과가 달라지고, 무엇을 보냈는지 서버가
  모르게 된다. 값과 위치 정보 둘 다 서버에서 못 박는 편이 낫다.

## 결과

무엇을 잃는가.

- **Pillow 의존성이 늘었다.** 이미지가 그만큼 무거워진다. 순수 파이썬으로 EXIF·리사이즈를
  다시 짜는 것보다 값이 싸다고 봤다.
- **느려질 수 있다.** 재시도가 걸리면 한 번 더 왕복한다. 최악은 두 배다. 얼마나 자주 걸리는지는
  `parse_usages.escalated` 로 세고, 잦으면 검증 기준을 느슨하게 하거나 1차 모델을 올린다.
- **검증 기준을 실측 없이 정했다.** 금액 상한 1억, 과거 730일, 미래 1일. 근거는 상식이지
  데이터가 아니다. 정상 입력을 막고 있으면 그 자리에서 고친다.
- **인식 품질을 여전히 안 쟀다.** 루나가 영수증을 실제로 얼마나 읽는지는 실기기 왕복 뒤에 안다.
  이 구조는 못 읽는 것을 **덜 위험하게** 만들 뿐, 잘 읽게 만들지는 않는다.
- **전처리가 글자를 지울 수 있다.** 테두리 잘라내기를 너무 세게 잡으면 가장자리 글자가 날아간다.
  35% 아래로 줄어들면 손대지 않게 막아 뒀지만, 실제 영수증으로 확인하지 않았다.
