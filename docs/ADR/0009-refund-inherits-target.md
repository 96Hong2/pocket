# 0009. 환불은 되돌리는 지출의 성격을 물려받고 그 금액을 넘지 못한다

상태: 확정 · **PRD 가 정하지 않아 우리가 정했다** · 2026-09-04 · [0005](0005-transfer-refund-aggregation.md) 를 보완한다

## 배경

[ADR-0005](0005-transfer-refund-aggregation.md) 가 "환불은 새 수입이 아니라 지출 취소" 라고 정했다.
표까지 만들어 두었는데, 그 표가 성립하려면 **환불 행 자체가 어떤 값을 갖는지**가 함께 정해져야 했다.
그걸 안 정해서 요청 본문이 보낸 값을 그대로 저장했고, 두 자리에서 규칙이 샜다.

리뷰가 실제로 재현했다.

```
예산 600,000 → 100,000 예산제외 지출(남은 예산 600,000, 정상)
             → 같은 건에 100,000 환불(예산제외 안 붙임) → 201
             → 남은 예산 700,000   ← 예산 총액보다 크다
```

```
10,000 지출 → 같은 건에 1,000,000 환불 → 201
            → month_expense -990,000 · 남은 예산 1,590,000
            → 같은 지출에 50,000 환불을 두 번 보내도 둘 다 201
```

환불이 지출 취소가 아니라 **돈을 만들어 내는 수단**이 됐다. 화면은 서버 값을 그대로 그리므로
사용자에게 그대로 보였다.

## 결정

환불을 저장할 때 서버가 다음을 강제한다.

| 규칙 | 내용 |
| --- | --- |
| 대상 확인 | 환불은 **내 지출**에만 연결한다 (기존) |
| 금액 상한 | `이미 붙은 환불 합계 + 이번 금액 ≤ 대상 금액`. 넘으면 422 `INVALID_REFUND_TARGET` |
| 성격 물려받기 | 환불 행의 `excluded_from_budget` 과 `category_id` 를 **대상 거래의 값으로 덮어쓴다.** 요청 본문 값을 쓰지 않는다 |
| 되돌린 환불 | `deleted_at` 이 있는 환불은 한도 계산에서 뺀다 |
| 수정 경로 | 환불이 걸린 지출의 종류 변경, 환불 행의 종류 변경, 상한을 넘기는 금액 수정을 모두 막는다 |

## 근거

- **파생값을 클라이언트가 정하게 두면 악의가 아니라 빠뜨림으로 규칙이 깨진다.** 환불 화면을 만들
  누구든 `excluded_from_budget` 을 실어 보내야 한다는 것을 알아야 하는데, 그건 화면이 알 일이 아니다.
- **저장 경로만 막으면 수정이 우회한다.** 실제로 `PATCH` 로 환불 대상을 수입으로 바꾸는 것과
  환불 금액을 100만원으로 올리는 것이 둘 다 200 이었다. 값이 바뀌는 문이 둘이면 검증도 둘이다.
- **되돌린 환불까지 한도에 세면 잘못 넣은 것을 고칠 수 없다.** 5만원짜리에 5만원을 잘못 넣고
  되돌린 뒤에는 아무것도 환불하지 못하게 된다.

## 대안

- **집계가 그때그때 대상을 읽는다**: `aggregate_period` 가 환불마다 대상 거래를 조회해
  예산 반영 여부를 정한다. 저장된 값을 안 건드려서 되돌리기 쉽지만, 순수 함수였던 도메인 계층이
  DB 조회를 하게 되고 집계 한 번에 쿼리가 거래 수만큼 늘어난다.
- **금액 상한을 두지 않고 화면에서만 막는다**: API 를 직접 부르는 쪽과 앞으로 붙을 캡처·영수증
  파싱 경로가 그대로 뚫린다. 그 경로들이 바로 M4~M6 다.
- **환불에 예산 제외를 아예 못 붙이게 한다**(항상 false): 예산에서 뺀 지출을 환불하면
  그 돈이 예산으로 돌아오는 지금 버그가 그대로 남는다.

## 무엇을 잃는가

- **저장된 환불 행의 `excluded_from_budget`·`category_id` 가 대상 값으로 굳는다.** 규칙을 뒤집으려면
  이미 쌓인 행을 백필해야 한다. 이 결정이 되돌리기 어려운 이유다.
- 요청 본문에 보낸 값이 응답에서 다르게 돌아온다. 코드만 읽으면 이상해 보인다. 그래서 이 기록을 남긴다.
- 부분 환불을 여러 번 받는 실제 상황에서, 대상 금액을 아주 조금 넘는 환불(수수료 환급 같은 것)이
  막힌다. 그때는 환불이 아니라 수입으로 적는 것이 맞다고 본다.

## 결과

- 검증은 `modules/transactions/service.py` 의 `_refund_target`·`_require_refund_consistency`
  두 함수에 모인다. 저장과 수정이 같은 것을 쓴다.
- 환불이 지출보다 커서 카테고리 지출·예산 진행률이 음수가 되는 것은 [0005](0005-transfer-refund-aggregation.md)
  대로 **그대로 둔다**(0 으로 자르지 않는다). 이 ADR 이 막는 것은 "대상보다 큰 환불" 이지
  "음수 집계" 가 아니다.
- `tests/api/test_transactions_guards.py` 가 여섯 경우를 고정한다: 상한 초과, 중복 환불,
  되돌린 환불의 한도 반환, 예산 제외 물려받기, 수정으로 종류 바꾸기, 수정으로 금액 키우기.
