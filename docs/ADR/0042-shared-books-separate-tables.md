# 0042. 공유 가계부 기록은 거래 표에 섞지 않고 새 표에 둔다

상태: 확정 · 2026-09-28 · PRD 가 저장 방식을 정하지 않아 우리가 정함

## 배경

공유 가계부(연인·부부, 가족, 여행·모임, 룸메이트)를 1차로 연다. 링크 하나로 들어온 사람이
설명 없이 첫 공동 지출을 적을 수 있어야 한다. 같이 쓴 돈은 멤버 모두가 보고 고치고,
누가 냈는지로 정산한다.

지금 기록은 전부 `transactions` 한 표에 있고 주인은 `user_id` 하나다. 개인 조회는 그 칸으로
거른다. `backend/app` 에서 `user_id ==` 조건을 세면 67곳이다(2026-09-28, 공유 가계부 모듈 제외).
거래 목록, 달력, 요약, 예산, 리포트, 결산, 피드백 판정, 내보내기, 합치기, 초기화가 다 이 조건을 탄다.

두 길이 있었다.

| 안 | 모양 |
| --- | --- |
| A. 거래 표에 칸을 더한다 | `transactions.book_id` 를 두고, 공유 기록은 `book_id` 가 찬 거래로 적는다 |
| B. 새 표를 둔다 | `books`, `book_members`, `book_invites`, `book_categories`, `book_entries`, `settlements` |

## 결정

**B. 공유 기록은 `book_entries` 에 적고 개인 표에는 칸 하나 더하지 않는다.**

- 개인 조회 67곳은 그대로 둔다. 공유 기록이 개인 합계, 예산, 리포트, 피드백에 들어갈 길이 처음부터 없다.
- 공유 쪽 조회는 전부 「이 가계부의 지금 멤버인가」 를 먼저 본다(`books/service._access`). 아니면 404 다.
- 두 쪽을 잇는 곳은 옮기기 둘뿐이다(`move-out`, `move-in`). 만들기와 원본 지우기를 한 commit 으로 묶는다.
- 사람을 가리키는 칸은 사용자 줄이 아니라 **멤버 줄을 `SET NULL`** 로 본다.
- 분류는 가계부마다 따로 심는다(`book_categories`). 개인 분류를 빌려 쓰지 않는다.
- 금액 규칙(양수, 원 단위, `numeric(14,0)`)과 집계 규칙(`domain/aggregation`)은 그대로 쓴다.

## 근거

**새는 자리를 만들지 않는다.** A 로 가면 67곳 하나하나에 `book_id IS NULL` 을 더해야 한다. 한 곳만
빠뜨려도 멤버의 지출이 내 합계에 더해지거나 내 개인 지출이 상대 화면에 뜬다. 그런 결함은 테스트가
그 화면을 짚어야만 보인다. B 는 개인 쪽 코드를 안 고치므로 빠뜨릴 자리가 없다.
「개인 기록이 공유로 새지 않는다」 는 API 테스트(C42)가 이 결정을 지킨다.

**주인 개념이 다르다.** 거래는 한 사람 것이라 `user_id` 하나로 충분하다. 공유 기록에는 적은 사람,
낸 사람, 고친 사람, 지운 사람이 따로 있고 모두 가계부 멤버다. 거래 표에 이 칸 넷을 얹으면 개인
거래에서는 늘 비어 있는 칸이 된다.

**분류가 서로 안 보인다.** 개인 분류는 기본 분류와 내 것만 보인다. 한 멤버가 만든 분류를 공동 기록에
달면 상대 화면은 그 id 를 못 푼다. 가계부마다 분류를 심으면 멤버 모두가 같은 목록을 본다.

**한 사람 줄이 지워져도 상대 기록은 남아야 한다.** 거래 표의 `user_id` 는 CASCADE 다. 공유 기록을
거기 두면 한 사람 줄이 지워질 때 같이 쓴 돈까지 사라진다. 멤버 줄을 `SET NULL` 로 보면 기록은 남고
「나간 멤버」 로 보인다.

**날짜의 뜻이 다르다.** 거래는 시각(UTC)을 저장하고 사용자 시간대로 날을 다시 뽑는다. 멤버마다
시간대가 다르면 같은 기록이 사람마다 다른 날에 선다. 공유 기록은 적는 사람 화면의 날짜를 그대로
`occurred_on` 에 두고, 가계부 시간대는 「오늘」 과 멤버 기간을 가를 때만 쓴다.

## 대안

- **A. `transactions.book_id`**: 공유 기록이 개인 목록과 검색에 저절로 섞여 보이는 장점이 있다.
  그러나 67곳을 고쳐야 하고, 빠뜨린 자리가 곧 개인정보가 새는 자리다. 버렸다
- **A 에 DB 뷰나 행 보안(RLS)을 얹어 막기**: 개인 조회가 늘 `user_id` 로 거르므로 뷰로 막을 자리가
  없고, RLS 는 연결마다 사용자를 심는 기반이 필요하다. 1차 규모에 비해 크다
- **공유 기록을 멤버마다 거래로 복제하기**: 한 사람이 고치면 나머지 사본을 다 맞춰야 하고, 합계가
  멤버 수만큼 부풀지 않게 또 막아야 한다. 같은 돈이 여러 줄에 있게 된다

## 결과 (무엇을 잃는가)

- **개인 목록과 검색에 공유 기록이 안 보인다.** 내가 낸 공동 지출을 내 가계부에서도 보려면
  「내 가계부로 옮기기」 를 눌러야 하고, 옮기면 공유 쪽에서는 빠진다. 한 기록이 두 곳에 동시에 있지 않다
- **집계 코드를 두 번 부른다.** 공유 리포트는 기록을 `TransactionInput` 으로 바꿔 같은 도메인 함수를
  태운다. 규칙은 하나지만 불러오는 자리는 둘이다(`reports/service`, `books/service`)
- **홈의 기록 이력(연속 기록, 오랜만에 온 사람 판정)은 개인 거래만 센다.** 공유 가계부에만 적는 사람은
  개인 홈에서 처음 쓰는 사람처럼 보일 수 있다
- 개인 기능 중 공유 쪽에 없는 것이 생긴다: 수입, 이체, 환불, 태그, 결제 수단, 줄글·캡처·영수증 입력.
  1차는 지출만 받는다
- 옮기기에서 분류는 **같은 이름**으로만 이어진다. 이름이 다르면 「기타」 로 간다
- 이메일로 계정을 합칠 때 멤버 줄을 따로 옮겨야 한다(`books.absorb_memberships`). 안 옮기면 접힌
  계정에 멤버 줄이 남아 그 사람이 공유 가계부를 잃는다

## 뒤집을 조건

- 공유 기록과 개인 기록을 한 목록에서 함께 봐야 한다는 요구가 굳어지면, 표를 합치기 전에 조회 쪽에서
  두 목록을 이어 붙이는 길을 먼저 본다
- 공유 쪽에 수입, 환불, 태그가 들어와 개인 거래와 칸이 거의 같아지면 다시 따져 본다
