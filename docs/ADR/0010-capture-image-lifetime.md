# 0010. 캡처 이미지는 요청이 끝나면 사라지고, 한 번에 한 장만 받는다

상태: 확정 · **PRD 가 정하지 않아 우리가 정했다** · 2026-09-05

## 배경

PRD F13 은 "원본 이미지는 파싱 후 삭제" 라고만 적는다. **삭제가 언제 일어나는지, 지우는 코드가
어디 있어야 하는지는 정하지 않았다.** 삭제를 '나중에 하는 일' 로 두면 지울 자리가 생기고,
지울 자리가 있으면 언젠가 잊는다. 임시 파일 하나, 실패 경로 하나면 캡처가 디스크에 남는다.

같이 걸린 것이 둘 더 있었다.

- `ARCHITECTURE.md` 의 입력 경로 그림은 `결제 알림 캡처(여러 장) → OCR + LLM 구조화` 였는데,
  코드에는 OCR 이 한 줄도 없다. 그림이 없는 단계를 있는 것처럼 그려 두면 다음 사람이 그 단계를
  찾다가 만들게 된다.
- 포트 `LlmStructuredClient.extract` 는 `image` 를 **한 장만** 받는다. PRD F4 의 '여러 장' 과
  어긋난 채로 남아 있었다.

## 결정

| 항목 | 정한 것 |
| --- | --- |
| 삭제 시점 | 서버는 이미지를 파일로 쓰지 않고 임시 디렉터리도 쓰지 않는다. **요청 처리가 끝나 파이썬 객체가 회수되는 것이 삭제다** |
| 지나는 자리 | data URL 을 바이트로 푸는 것은 `backend/app/api/images.py` 한 곳만 한다 |
| 남기는 것 | 구조화된 후보와 `parse_usages` 계측(바이트 수·후보 건수)뿐 |
| OCR | 단계를 두지 않는다. vision 모델이 이미지를 직접 읽는다 |
| 장수 | 한 번에 한 장. 포트 계약이 그렇다 |
| 가리기 | 이미지 안의 카드번호·계좌·잔액은 **가리지 못한다.** `redact()` 는 문자열 전용이다 |

## 근거

- **지울 단계가 없으면 잊을 자리가 없다.** 요청 안에서 동기로 끝나므로 이미지를 어디에 둘 이유가
  없다. '지우는 것을 기억해야 하는 코드' 를 애초에 만들지 않는 것이 가장 확실한 삭제다.
- **한 파일로 가두면 "이미지가 어디까지 갔다 사라지나" 를 한 파일만 보면 답할 수 있다.**
  형식·mime·크기·매직바이트 검사가 흩어지면 어느 하나가 빠진 것을 알아채지 못한다.
- **OCR 을 넣으면 남기지 않기로 한 원문이 하나 더 생긴다.** `DATA_MODEL.md` 의 저장 금지 항목이
  OCR 원문을 이미 막고 있는데, 그러면 그 단계는 계산에 쓰이고 바로 버려지는 중간 산물이 된다.
  단계만 늘고 샐 자리가 는다. vision 모델이 직접 읽으면 이미지에서 후보까지 한 걸음이다.
- **한 장 제한은 새로 만든 제약이 아니라 이미 있던 계약이다.** 여러 장은 포트를 넓히는 일이라
  앨범 한 갈래가 실기기에서 도는 것을 본 뒤에 하는 편이 싸다.

## 대안

- **이미지를 임시 파일로 쓰고 `finally` 에서 지운다**: 비동기 분석과 재시도를 나중에 붙이기
  쉬워진다. 그런데 지우는 코드가 실패 경로마다 필요하고, 한 곳만 빠져도 캡처가 디스크에 남는다.
  지금은 동기로 한 번에 끝나므로 파일이 필요한 이유 자체가 없다.
- **원본을 짧은 TTL 로 객체 저장소에 둔다**(오인식을 다시 보려고): 인식 품질을 올리는 데 실제로
  쓸모가 있다. 대신 저장소·수명주기·접근권한·삭제 요청 처리가 통째로 늘고, 없던 유출 표면이
  생긴다. provider 도 안 고른 단계에서 지불할 값이 아니다.
- **OCR 을 먼저 돌리고 텍스트만 모델에 보낸다**: 텍스트가 되면 `redact()` 를 태울 수 있어 아래
  '무엇을 잃는가' 의 가리기 문제가 풀린다. 그런데 OCR provider 가 하나 더 늘고 **그쪽에는 원본이
  그대로 간다.** 가린 뒤 보내는 것은 두 번째 provider 뿐이라 문제를 옮길 뿐이다. 넷 중 다시 볼
  값어치가 있는 유일한 안이라 여기 적어 둔다.
- **여러 장을 한 번에 받는다**: PRD F4 가 적은 그대로다. 포트 계약을 넓히고 후보 정렬·묶음 안
  중복 판정을 함께 손봐야 해서, 캡처 한 갈래가 실기기에서 도는 것을 본 적이 없는 지금 하기에는
  범위가 크다.

## 무엇을 잃는가

- **이미지 안의 카드번호·계좌번호·잔액을 가리지 못한 채 provider 로 나간다.**
  `app/domain/redaction.py` 의 `redact()` 는 문자열 전용이고, 캡처 경로에는 그 단계가 아예 없다.
  `SECRETS.md` 의 "모델에 보내기 전에 가린다" 는 줄글에서만 성립한다. 설계로 메울 수 없어서
  provider 계약(zero-retention 여부)으로 받기로 한다. `parse_usages.redacted_count` 가 캡처에서
  늘 0 인 것이 이 사실이 표에 남은 모습이다.
- **오인식을 나중에 다시 볼 원본이 없다.** 사용자가 "이거 틀렸어요" 라고 해도 무엇을 보냈는지
  아무도 모른다. 남는 실마리는 거래의 `import_batch_id` 와 `parse_usages` 한 줄뿐이다.
- **운영 트래픽으로 인식 품질 회귀 세트를 만들 수 없다.** 재려면 평가용 이미지를 따로 모아야 한다.
- **비동기 분석·재시도를 붙이려면 이미지를 다시 받아야 한다.** 요청 안에서 끝나는 구조라 큐에
  넣을 것이 남지 않는다.
- 여러 장 캡처를 지금 주지 못한다. PRD F4 에 적힌 것을 한 장으로 좁힌 것이다.

## 결과

- `app/api/images.py` 가 형식 → mime → 디코드 → 크기 → 매직바이트 순서로 본다. 허용 형식은
  `image/png`·`image/jpeg`·`image/webp` 셋이고 디코드 후 상한은 4MiB 다. 실패는 어디서 걸렸든
  422 `INVALID_REQUEST` 에 "사진을 읽지 못했어요." 하나다. 이유를 나누면 그 메시지가 곧 입력에
  대한 정보가 된다.
- 그 파일에만 있는 규율: **예외 메시지·로그·트레이스백에 입력 값이나 그 조각을 넣지 않는다.**
  base64 한 토막만 새어도 캡처 원문이 복원된다. `LlmImage.__repr__` 도 길이만 남긴다.
- 스키마의 문자열 길이 상한 6,000,000 은 본문이 메모리에 들어오기 전에 거는 한 겹일 뿐이다.
  진짜 상한은 디코드한 뒤의 4MiB 다.
- `ImportBatchStatus` 의 `pending`·`analyzing`·`failed` 는 쓰이지 않는다. 동기로 끝나므로 묶음은
  만들어질 때부터 `ready` 다. 비동기를 여는 날 되살린다.
- **인식 정확도는 이 결정이 증명하지 않는다.** vision provider 가 아직 없어서 스텁이 이미지를
  읽지 않고 정해 둔 5건을 낸다. 응답의 `meta.notes` 에 실리는 `stub_image` 가 화면에 그 사실을
  띄운다.
- 되돌리려면 이 ADR 을 대체하는 새 ADR 과 함께 저장소·수명주기·접근권한·삭제 요청 처리를 같이
  정해야 한다. 코드 한 줄로 뒤집는 결정이 아니다.
