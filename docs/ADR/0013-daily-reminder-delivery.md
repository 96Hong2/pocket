# 0013. 기록 알림은 하루 한 번, 서버가 고르고 어댑터가 보낸다

상태: 확정 · **발송 API 는 아직 우리 손에 없다(어댑터 자리만 뒀다)** · 2026-09-08

## 배경

기록 알림을 붙이기로 했다. 그런데 알림은 잘못 만들면 이 앱이 하지 않기로 한 것을 정확히
하게 된다. 며칠 안 적은 사람에게 "밀렸다" 고 말하고, 열 때마다 동의를 묻고, 하루에 여러 번
울린다. 무엇을 언제 보낼지를 정해 두지 않으면 그 셋이 하나씩 슬며시 들어온다.

만드는 쪽에도 막힌 곳이 있었다. **토스 스마트발송을 서버에서 부르는 API 를 확인하지 못했다.**
SDK 타입 정의(`@apps-in-toss/web-framework`)에는 앱에서 동의를 받는 함수만 있고, 서버가
실제로 알림을 쏘는 경로는 문서에도 타입에도 없다. 기억으로 API 이름을 지어내는 것은
저장소 절대 규칙이 막고 있다.

## 결정

**보내는 것은 하나뿐이다: 매일 정한 시각에 "적으러 오라" 는 알림 한 통.**

- 화면에 있는 것은 **켜기와 시각 둘**이다. 빈도를 고르는 자리를 두지 않고, 켤 때 `daily` 로 보낸다.
- **동의는 켜는 그 순간에만 묻는다.** 화면에 들어온 것만으로는 묻지 않는다.
  거절(`agreementRejected`)은 오류가 아니라 결과의 한 종류이고, **다시 묻지 않는다.**
- **시간대 정본은 `users.timezone`** 이다. `notification_settings.timezone` 컬럼은 초기
  스키마에 남아 있지만 읽지 않는다.
- 보낼 때인지는 순수 함수 `domain/reminders.is_due` 가 판정한다:
  **정한 시각과 현지 시각의 분이 같고, `last_reminded_on` 이 오늘이 아니면** 보낸다.
- 발송기는 `backend/scripts/send_reminders.py` 이고 **1분마다** 불린다(`--dry-run` 이 있다).
  실제로 쏘는 것은 `app/integrations/notifications/` 의 어댑터이고, 지금 붙어 있는 것은
  로그로 남기는 스텁(`LogReminderSender`)이다.
- 알림 본문에 **금액도 기록 내용도 싣지 않는다.** 발송 대상에 담는 것은 사용자 id·현지 날짜·시각뿐이다.

## 근거

- **하루 한 번으로 못 박은 이유.** 여러 번 보내는 순간 '얼마나 자주' 를 고르는 화면이 필요해지고,
  그 화면은 곧 "더 자주 받으면 더 잘 적는다" 는 말을 하게 된다. 이 앱은 행동을 늘리라고
  재촉하지 않기로 했다.
- **분이 정확히 같을 때만 보낸다.** '그 시각이 지났으면 보낸다' 로 두면 발송기가 한 시간
  멈춘 뒤 깨어났을 때 밤 9시 30분 알림이 밤 10시 30분에 간다. 늦게 온 알림은 '지금 적으라'
  는 말이 아니게 된다. 그 날은 건너뛰는 쪽이 낫다.
- **보낸 날을 남긴다.** 발송기가 겹쳐 돌거나 재시도가 끼면 같은 분에 두 번 깨어난다.
  날짜만 남기면 '오늘 보냈나' 하나를 답할 수 있고, 몇 시에 보냈는지는 로그가 안다.
- **실패하면 보낸 날을 남기지 않는다.** 남겨 버리면 못 보낸 날이 보낸 날로 굳는다.
- **시간대를 사용자 것으로 본다.** UTC 로 견주면 한국에서 밤에 받기로 한 알림이 낮에 간다.
  월 경계를 사용자 시간대로 보는 규칙과 같은 자리에 둔다.
- **거절을 오류로 다루지 않는다.** 거절은 사용자가 고른 결과다. 실패로 다루면 '다시 시도'
  버튼이 붙고, 그 버튼은 거절한 사람에게 같은 것을 또 묻는 장치가 된다.
- **어댑터 자리만 둔 이유.** 발송 API 를 모르는 채로 어댑터를 지어내면 배관 전체가
  검증되지 않은 가정 위에 서게 된다. 대신 **누구에게 언제 보낼지 고르고 보낸 날을 남기는
  부분은 지금 전부 돌고**, 그 자리는 테스트가 지킨다. 실제 경로가 열리면 파일 하나가 는다.

## 대안

- **밀린 날을 세어 알리기**("사흘째 기록이 없어요"): 벌주지 않기로 한 규칙과 정면으로 부딪힌다.
  복구 카드가 이미 담담한 말로 그 자리를 맡고 있다.
- **주 2회·매일 중에 고르게 하기**: 모델에 `weekly_twice` 가 있어 열 수는 있었다. 고르는 화면이
  하나 더 늘고, 무엇을 골라야 좋은지 사용자가 판단할 근거가 없다.
- **시각을 지나면 늦게라도 보내기**: 위 근거대로 늦은 알림은 뜻이 달라진다. `last_reminded_on`
  이 있으니 나중에 창을 넓히는 것은 한 줄이다. 넓히려면 이 ADR 을 고친다.
- **동의 여부를 서버에 저장하기**: 토스 앱 설정에서 언제든 바뀌는 값이라 서버 사본은 곧 낡는다.
  켤 때마다 앱에 물어보는 것이 늘 맞는 답이다.
- **진입하자마자 동의를 묻기**: 켤 생각이 없는 사람에게도 창이 뜬다. 심사에서도 사유가 된다.

## 결과

- API 는 `GET`·`PATCH /api/v1/notifications/settings` 둘이다. 조회가 없는 행을 기본값으로 만들어 준다.
- `PATCH` 에서 **`remind_at` 만 `null` 이 '지움'** 이다. 다른 설정(`/preferences`)과 규칙이 반대라
  스키마 docstring 과 `docs/API_CONTRACT.md` 에 함께 적었다.
- 켜면서 시각을 안 주면 서버가 **21:30** 을 넣는다. 켜 두고 시각이 비면 영영 안 가는 알림이 된다.
- 템플릿 코드는 `VITE_NOTIFICATION_TEMPLATE_CODE` 로만 들어온다. 비어 있으면 개발에서는
  통과시키고 운영 빌드에서는 못 쓰는 기능으로 다룬다(광고 그룹 ID 와 같은 방식이다).
- 낮은 토스 앱 버전에서 못 쓰는 갈래는 **e2e 로 볼 수 없다**(devtools 목의 `isSupported` 가 늘
  true 다). 그 갈래는 `frontend/tests/notification-bridge.test.ts` 가 지킨다.
