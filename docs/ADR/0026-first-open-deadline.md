# 0026. 첫 화면은 서버에 닿지 않아도 20초 안에 선다

상태: 확정 · 2026-09-20

## 배경

번들 두 개가 잇달아 반려됐다.

| 번들 | 사유 |
|---|---|
| `20260919-33` | 1. 앱 스킴 접속이 불가능해요. 앱 메인 스킴으로 접속이 되지 않아요. |
| `20260920-35` | 1. 미니앱 최초 접속 시간이 20초를 초과하여 로딩 성능 개선이 필요해요. |

33 을 조사할 때 **제출부터 반려까지 우리 서버에 앱 요청이 한 건도 없었다.** 승인된 26 때는
제출 3분 뒤 Android 검수 기기가 들어와 홈·리포트·관리를 돌고 기록까지 남겼다. 코드에서
원인을 못 찾아 그대로 뒀는데, 35 의 사유가 같은 자리를 다른 말로 가리켰다.

부팅에 **끝나지 않을 수 있는 기다림이 둘** 있었다.

1. `User.getAnonymousKey()` 에 제한 시간이 없었다. 실패하면 되묻고 안내를 띄우지만,
   **답이 아예 안 오면 잡을 자리가 없다.** 화면은 「불러오는 중」 에 갇히고, 그동안 조회·저장은
   식별키를 기다리느라 서버로 한 건도 안 나간다. 33 의 서버 로그가 비어 있던 이유가 이것이다.
2. 조회 마감이 10초, 재시도가 2회였다. 서버에 닿지 않는 자리에서 10 + 1 + 10 + 2 + 10 = 33초다.
   그동안 홈은 기록 버튼조차 안 그린다.

**서버가 느린 것은 아니다.** 한때 `/health` 가 6.5초 걸린 것을 콜드 스타트로 읽었는데, 다시 재 보니
150ms 였고 그날 컨테이너 시작 기록도 0건이었다. Cloud Scheduler 워머(`pocket-backend-warm`, 5분)와
알림 틱(1분)이 이미 컨테이너를 붙잡고 있다. 문제는 서버 속도가 아니라 **클라이언트가 기다리는 방식**이었다.

## 결정

- **식별키 조회에 마감을 건다.** 한 번에 2.5초, 세 번까지(`2.5 + 0.6 + 2.5 + 1.8 + 2.5 = 9.9초`).
  넘기면 `TIMEOUT` 으로 실패 처리하고 「다시 시도」 를 띄운다. 실기기에서 이 호출은 0.5초를 안 넘는다.
- **조회 마감을 6초로, 재시도를 1회로 줄인다.** 최악이 `6 + 1 + 6 = 13초`다.
  줄글 읽기·사진 읽기처럼 원래 오래 걸리는 자리는 저마다 더 긴 값을 따로 넘긴다.
- **기록 버튼은 조회를 기다리지 않는다.** 홈은 예산 조회가 끝날 때까지 화면을 통째로
  스피너로 덮고 있었다. 이제 히어로 자리만 기다리고 기록 버튼은 바로 선다. 조회가 실패했을
  때 버튼을 남기는 규칙은 원래 있었는데, **기다리는 동안에는 안 걸려 있었다.**
- **20초를 검증으로 못 박는다.** `e2e/specs/slow-first-open.spec.ts` 가 모든 API 요청을 붙잡아
  답하지 않는 자리에 앱을 놓고, 기록 버튼이 3초 안에, 「다시 시도」 가 20초 안에 서는지 잰다.

## 근거

- **답이 안 오는 것은 실패보다 나쁘다.** 실패는 화면이 말할 수 있지만, 안 끝나는 기다림은
  고장인지 느린 것인지 구분할 방법이 없다. 사람도 검수 기기도 같은 것을 본다.
- **검수는 사람이 눈으로 보는 것이 아니다.** 20초라는 선이 있고 넘으면 반려다. 여유를 두고
  「대개 빠르다」 로는 안 된다. 최악의 경로가 선 안에 들어와야 한다.
- **일부러 되돌려 확인했다.** 재시도를 3회로 올리자 20초 안에 기록 버튼조차 안 떴다.
  검수 기기가 본 화면이 그것이다.
- **숫자를 줄이는 것만으로는 모자라다.** 마감을 6초로 줄여도 기록 버튼이 13초를 기다렸다.
  기다리는 화면과 쓰는 화면을 갈라야 망이 어떻든 첫 화면이 1초 안에 선다.

## 버린 안

| 버린 안 | 왜 |
|---|---|
| Cloud Run 을 항상 한 대 띄워 둔다(`min-instances=1`) | **필요 없다.** Cloud Scheduler 가 `/health` 를 5분마다, 알림 틱이 1분마다 두드려서 컨테이너가 안 내려간다. 2026-09-20 하루 동안 컨테이너 시작 기록이 0건이고 `/health` 는 150ms 다 |
| 첫 화면을 캐시로 그리고 나중에 맞춘다 | 틀린 숫자를 먼저 보여 준다. 가계부에서 금액이 한 번 잘못 보이면 그 뒤 숫자를 못 믿는다 |
| 조회 마감만 줄이고 식별키는 둔다 | 식별키가 안 오면 조회는 **아예 안 나간다.** 마감을 줄여도 화면은 그대로 갇힌다 |
| 재시도를 0으로 | 지하철에서 한 번 흔들린 것까지 오류 화면이 된다. 한 번은 남긴다 |

## 무엇을 잃는가

- **아주 느린 망에서 6초를 넘기면 오류 화면이 뜬다.** 예전에는 10초까지 기다렸다.
  대신 「다시 시도」 가 있고, 그 버튼은 마감을 새로 센다.
- 식별키를 2.5초 안에 못 주는 기기에서는 안내 화면을 한 번 보게 된다. 눌러서 다시 받으면 된다.
- 첫 조회는 여전히 망 사정을 탄다. 서버 자체는 150ms 안에 답한다(워머가 붙어 있다).
