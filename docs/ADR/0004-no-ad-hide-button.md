# 0004. 광고 배너에 X(숨기기) 버튼을 넣지 않는다

상태: 확정 · 2026-09-03

## 배경

시안(mockup)은 광고 배너에 `✕ 숨기기` 버튼, 자체 `AD · 토스 광고` 라벨, 높이 76px 을 그렸다.
PRD v4.1 §10 도 "가능하면 X 로 숨길 수 있게" 라고 적었다. 다만 같은 문장에 "출시 전 정책 재확인 후 허용 안 되면 제거" 라는 조건을 달아 뒀다.
그 재확인을 했다.

## 결정

X(숨기기) 버튼을 넣지 않는다. 자체 `AD` 라벨도 그리지 않는다. 슬롯 내부는 비워 두고 SDK 에 맡긴다.

## 근거

SSP 정책 세 조항에 동시에 걸린다.

- **광고 은닉 또는 겹침**: "광고를 의도적으로 숨기거나 다른 UI 요소에 가려 사용자가 광고의 존재를 명확히 인지하기 어렵게 만드는 행위" 를 금지한다. 숨기기 버튼은 이름 그대로 은닉 수단이다.
- **UI/UX 품질 저하**: "광고 UI 임의 수정 금지, 모든 광고 UI 는 표준 컴포넌트 사용". 우리가 버튼과 라벨을 얹는 것이 곧 임의 수정이다.
- **포괄 조항**: "정책에 명시되지 않았더라도 사용자에게 오해를 만드는 행위는 위반으로 본다". 애매한 쪽은 하지 않는 것이 맞다.

심사 반려나 광고 계정 제재의 손해가, 사용자가 배너를 접을 수 있어서 얻는 이득보다 훨씬 크다.

## 대안

- **X 버튼을 넣고 심사 결과를 본다**: 통과하면 이득이지만 반려되면 재심사까지 출시가 밀린다. 실험 비용이 비대칭이다.
- **X 대신 "광고 없애기(Pro 결제)" 버튼**: 결제가 MVP 밖이다. Pro 가 생기면 다시 검토한다.

## 결과

- 컨테이너는 `width: 100%`, `height: 96px`. `width` 를 px 로 고정하는 것은 공식 문서가 나쁜 예로 든다.
- 내부에 우리 마크업(스켈레톤·라벨·테두리)을 넣지 않는다. `Ad` 표기는 SDK 가 그린다.
- **우리가 새로고침하지 않는다.** SDK 가 (렌더 10초 경과 + visibility false→true) 조건으로 자동 갱신한다. 타이머로 destroy + attach 를 반복하는 것은 "광고 영역 주기적 Refresh" 로 성과 조작에 해당한다. 화면 재마운트도 사실상 refresh 라서 **배너는 홈 한 곳에만** 둔다. → 2026-09-11 개정, 아래 참고.
- `isSupported` / `onNoFill` / `onAdFailedToRender` 를 모두 처리하고, 광고가 없으면 빈 자리를 남기지 말고 **슬롯 자체를 접는다**.
- 개발·테스트는 공식 테스트 ID `ait-ad-test-banner-id` 를 쓴다. 운영 ID 는 하드코딩하지 않고 환경변수로 넣는다.

## 근거 원문

배너 규격(가로 100%, 높이 96px, 내부 비움, 자동 갱신 조건, 테스트 ID)의 정본은
`documentation/common/monetization/iaa/web-banner.md` 다.
금지 행위 표(광고 은닉·UI 임의 수정·주기적 Refresh)는 `guide/monetization/in-app-ad.md` 에 있다.
`.md` 를 붙여 `curl` 로 받으면 원문을 그대로 볼 수 있다.


## 개정 (2026-09-11): 자리는 여섯, 대신 자리마다 재요청 간격을 둔다

위 결과 항목의 "배너는 홈 한 곳에만" 을 바꾼다. 배너를 **홈·리포트·관리·앱 설정·자산·목표**
여섯 자리에 둔다(처음 개정 때는 넷이었고, 실기기로 보고 자산·목표를 더했다).
X 버튼과 자체 라벨을 넣지 않는다는 이 문서의 결정 자체는 그대로다.

### 왜 바꿨나

한 자리로는 수익이 나지 않는다. 그리고 원래 우려는 "화면이 여럿" 이 아니라 **"같은 자리가 자주 다시
붙는 것"** 이었다. 서로 다른 화면에 배너가 하나씩 있는 것은 어느 정책 조항에도 걸리지 않는다.
걸리는 것은 탭을 오갈 때마다 같은 자리가 새 요청을 내보내 노출 수가 부풀려지는 쪽이다.

### 무엇으로 막나

- **자리마다 15초의 재요청 간격**(`features/ads/AdSlot.tsx`). 그 안에 같은 자리로 돌아오면 요청하지
  않고 슬롯을 접는다. 홈↔리포트를 빠르게 오가도 각 자리는 15초에 한 번만 요청한다.
- 슬롯은 각 화면에서 **조건부 형제들 사이의 고정된 한 자리**에 둔다. 모드나 데이터에 따라 사라졌다
  나타나면 그것이 곧 재마운트다.
- **자리는 화면 끝이다.** 관리에서 예산과 하위 화면 목록 사이에 뒀더니 할 일 흐름 한가운데를
  끊었다(실기기로 보고 알았다). 홈만 예외로 목록 위에 있다. 그 아래가 오늘 목록이라 끝이 없다.
- 결과(`shown` · `no_fill` · `failed` · `cooldown` · `no_group` · `opted_out`)를 `ad_result` 로 남긴다.
  운영에서 광고 ID 를 빠뜨린 채 배포하면 아무 오류 없이 조용히 접히므로, 이 로그가 유일한 실마리다.

### 테스트 판에서는 실광고를 붙이지 않는다

`Environment.environment` 가 `sandbox` 면 운영 광고 그룹 대신 공식 테스트 배너를 쓴다.
거기서 우리가 만든 앱을 우리가 눌러 보는 동안 실광고가 뜨면, 같은 기기·같은 아이피에서 반복
노출과 클릭이 쌓여 **무효 트래픽**으로 잡힌다. 막히면 되돌리는 데 오래 걸린다.
자리와 크기는 테스트 배너로도 똑같이 확인할 수 있다.

⚠ **QR 테스트가 어느 판으로 잡히는지는 아직 확인하지 못했다.** `sandbox` 라고 가정하고 짰지만
`toss` 로 잡히면 이 방어가 통째로 비껴간다. 확인 방법은 아래 개정 절에 있다.

## 개정 (2026-09-11 저녁): 판만으로는 못 막는다. 기기에서 끄는 길을 하나 둔다

위 절의 마지막 문단을 바꾼다. 원래는 「만든 사람이 자기 광고를 누르지 않는 것은 코드로 막을 수
없고, 테스트를 부탁할 때 말로 알린다」 였다.

말로 하는 부탁은 **누르지 않는 것만** 막는다. 무효 트래픽은 클릭만이 아니라 반복 노출로도 쌓이고,
스쳐 지나간 화면의 배너는 부탁으로 막히지 않는다. 판(`sandbox`)으로 가르는 방어도 QR 테스트가
`toss` 로 잡히는 순간 통째로 없는 것이 된다.

- **앱 설정 → 버전 줄 → 「앱 정보」 시트에 「이 기기에서 광고 끄기」 를 둔다.**
  켜면 그 기기에서는 광고를 안 붙인다(`shared/lib/adOptOut.ts`). 테스트 배너로 바꾸지 않는다.
  그것도 노출로 세어지기 때문이다.
- **접지는 않는다. 같은 크기의 빈 자리에 「광고 자리」 라고 적어 남긴다.**
  접어 버리면 배너가 들어갔을 때 화면이 어떻게 보이는지 확인할 수 없어, 정작 자리가 어색하지
  않은지를 못 본다. 이 빈 칸은 광고가 아니라 우리가 그린 것이라 「광고 변형」 과 무관하고,
  광고를 끈 기기에서만 보인다.
- 같은 시트가 **지금 판·배포 ID·기기 ID·토스 앱 버전**을 적는다. 실기기에서 판을 볼 자리가
  여기 말고는 없었다. 로그에는 실려 있지만 그 로그는 운영 판에서만 실제로 나간다.
- **기기 ID 는 화면에만 보여 준다. 로그에도 서버에도 보내지 않는다.**
  그 값이 로그에 실리면 익명 집계가 기기 단위 추적이 된다.

익명키로 제외 목록을 만드는 안은 버렸다. 키는 재설치하면 바뀌고, 목록에 넣는 순간 그것이 사람을
가리키는 값이 된다. 잃는 것은 자동화다. 테스터가 스위치를 직접 켜야 하고, 켜기 전 첫 화면의
노출 한 번은 막지 못한다.
