# 0008. 이미 자리를 차지한 행을 만나면 덮어쓴다

상태: 확정 · **PRD 가 정하지 않아 우리가 정했다** · 2026-09-03

## 배경

같은 모양의 문제가 두 곳에서 나왔다. **쓰려는 자리를 이미 다른 행이 차지하고 있을 때 무엇을
하느냐**다. 두 곳 모두 한 번 배포하면 되돌리기 어렵다. 기본 카테고리 id 는 배포된 DB 안에
영원히 남고, 예산 저장 방식은 프론트가 붙들 계약이 된다.

**기본 카테고리 시드.** `categories` 의 `(user_id, name)` 이 unique 이고 PostgreSQL 에서는
NULL 끼리도 같은 값으로 본다(`NULLS NOT DISTINCT`). 그래서 시드를 두 번 돌리면 두 번째가
터진다. 그런데 pytest 는 SQLite 로 돌고 SQLite 는 NULL 끼리 서로 다르게 봐서, 중복이 그냥
쌓이고 테스트는 통과한다. 실제로 시드를 두 번 돌려 SQLite 에서 22행이 되는 것을 확인했다.

**예산 저장.** `budgets` 의 `(user_id, period_start)` 가 unique 이고 소프트 삭제한 행도 그
자리를 지킨다. 자동 이어쓰기가 사용자가 지운 예산을 다음 조회에서 또 만들지 않게 하려고
일부러 그렇게 뒀다. 그래서 `POST` 로 만들면 두 번째 저장이 409 다. 지웠다 다시 저장하는
경우가 특히 나쁘다. 읽기로는 '예산 없음'인데 쓰기는 영구히 막힌다. 실제로 재현했다.

## 결정

**둘 다 멱등하게 만든다. 중복을 막는 일을 DB 제약에만 맡기지 않고 코드가 함께 한다.**

시드는 넣기 전에 이미 있는 이름을 읽어 빠진 것만 넣는다. 목록은 마이그레이션 파일 안에
값으로 박고 `app.domain.categories` 를 import 하지 않는다. id 는 고정 네임스페이스와 이름으로
만든 uuid5 다.

예산은 `POST` 가 아니라 `PUT /budgets?year=&month=` 하나다. 소프트 삭제한 행까지 찾아서,
있으면 금액을 덮고 `deleted_at` 을 지워 되살린다. 없으면 새로 만들되 `IntegrityError` 가 나면
롤백하고 다시 찾아 덮는다.

## 근거

- **적용이 끝난 리비전은 다시 돌아도 같은 결과여야 한다.** 마이그레이션이 도메인 목록을
  import 하면, 나중에 카테고리를 하나 추가하는 순간 이미 적용된 리비전의 의미가 같이 바뀐다.
  새로 만든 환경과 기존 환경의 DB 가 조용히 갈린다.
- **대신 드리프트는 테스트가 잡는다.** 값을 두 곳에 적는 대가는 어긋날 위험인데,
  `tests/test_default_category_seed.py` 가 마이그레이션의 목록과 `DEFAULT_CATEGORIES` 를
  통째로 비교한다. 도메인만 고치고 시드를 안 고치면 거기서 깨진다.
- **id 가 환경마다 다르면 안 된다.** 로컬·dev·운영에서 '식비'의 id 가 다르면 캡처 하나를
  옮겨 확인하는 것도 안 되고, 프론트가 특정 카테고리를 가리킬 방법이 없어진다. uuid5 는
  이름만 같으면 어디서 돌려도 같은 값을 준다.
- **tombstone 은 자동 복사를 막으려던 것이지 사용자를 막으려던 것이 아니다.** 사용자가 직접
  다시 정하는 것까지 영구히 막으면 그건 결함이다. 되살릴 때 `is_auto_carried` 를 false 로
  내려 "자동으로 복사된 예산" 이라는 배너가 거짓말하지 않게 한다.
- **PUT 이 의미와 맞다.** 한 기간에 예산은 하나뿐이라 만드는 것과 고치는 것을 사용자가 구분할
  이유가 없다. 화면이 "이미 있나" 를 먼저 물어보고 메서드를 고르게 만들 필요도 없다.

## 대안

- **시드에서 `app.domain.categories` 를 import 한다**: 값을 한 곳에만 적어 좋아 보이지만,
  과거 리비전의 의미가 바뀐다. 값 중복보다 이쪽이 나쁘다.
- **`INSERT ... ON CONFLICT DO NOTHING`**: 한 줄로 끝나지만 SQLite 와 PostgreSQL 에서 NULL 을
  다르게 봐서 테스트가 실제 동작을 못 덮는다. 게다가 이름은 같은데 id 가 다른 행이 이미 있으면
  여전히 터진다.
- **`POST` + 409 를 화면이 받아 `PATCH` 로 다시 보낸다**: 왕복이 두 번이 되고, 지워진 예산은
  어차피 되살릴 방법이 없다.
- **하드 삭제로 tombstone 을 없앤다**: unique 충돌은 사라지지만 자동 이어쓰기가 사용자가 지운
  예산을 다시 만든다. 문제를 다른 곳으로 옮기는 것이다.

## 결과

- 시드 id 두 개를 테스트에 값으로 박아 뒀다. 네임스페이스를 바꾸면 거기서 깨진다.
- 시드 멱등성은 실제 PostgreSQL 로 확인한다. SQLite 는 이 결함을 못 잡는다.
- 예산 금액은 1원 이상만 받는다. 0원은 '예산 없음'(`amount: null`)과 구분되지 않는데다
  게이지 비율의 분모가 0 이 되어 화면이 그릴 수 없다.
- 예산 삭제 엔드포인트가 생겼다(`DELETE /budgets`, `DELETE /budgets/categories/{id}`). 여기서
  정한 대로 tombstone 을 남기는 방식을 그대로 쓴다. 삭제가 남긴 표시가 자동 이어쓰기를 막는
  근거로 실제로 쓰이고, 사용자가 그 기간을 직접 다시 정하면 같은 행을 되살린다.
- 그래서 쓰기 경로도 조회와 똑같이 이어쓰기를 한 번 지난다. 새 달의 첫 요청이 지우기이면
  아직 이어쓸 행이 만들어지지 않아 지울 것이 없고, 표시를 남기지 못한 채 204 가 나간다.
  그 뒤 조회가 지난달 예산을 이어써서 방금 지운 예산을 되살린다.
