# 0017. 기록 알림은 토스 스마트발송으로 보내고, 그 대상 익명키는 알림을 켠 동안만 보관한다

상태: 확정 · **PRD 가 정하지 않아 우리가 정했다** · 2026-09-10

## 배경

ADR-0013 이 "서버가 고르고 어댑터가 보낸다" 까지 정해 두고 어댑터 자리만 비워 뒀다. 그때는
토스 스마트발송을 서버에서 부르는 API 를 못 찾아서, 있다고 가정한 코드를 지어내지 않았다.

찾았다. 파트너 서버에서 앱인토스 서버로 부르는 서버 간 호출이고, 인증은 **우리가 이미 붙여
놓은 익명키 검증용 mTLS 인증서와 같은 것**을 쓴다.

```
POST /api-partner/v1/apps-in-toss/messenger/send-message
헤더  x-anon-key 또는 x-toss-user-key
본문  {"templateSetCode": ..., "context": {...}}
```

그런데 부를 수가 없었다. 보낼 사람을 `x-anon-key` 로 말해야 하는데, 우리는 익명키 원문을
저장하지 않는다. `users.anon_key_hash` 는 sha256 이라 되돌릴 수 없다(ADR-0003, `api/deps.py`).
요청 안에서는 원문이 있지만 잡은 요청 밖에서 돈다.

## 결정

1. **어댑터를 만든다.** `TossSmartMessageSender` 가 기존 `TossApiClient` 를 그대로 쓴다.
   새 인증서도 새 의존성도 없다. **부르는 방법(경로·헤더·응답 모양)은
   `integrations/apps_in_toss/smart_message.py` 에 둔다**(AI 개발 규칙 §3). 헤더 이름은
   익명키 검증의 것을 import 한다. 사본을 두면 토스가 이름을 바꿀 때 한쪽만 고치게 된다.
2. **익명키 원문을 `notification_settings.push_anon_key` 에 둔다.** `users` 가 아니다.
3. **수명을 동의와 같게 맞춘다.** 켤 때 채우고, **끄면 그 자리에서 지운다.** 알림을 안 쓰는
   사람의 익명키는 우리 DB 어디에도 없다.
4. **다시 부르지 않는다.** 발송 호출에 `idempotent=False` 를 **명시적으로 넘긴다.** 기본값에
   기대면 공통 클라이언트가 바뀌는 순간 같이 바뀐다. Cloud Run 잡도 `--max-retries=0` 이다.
5. **0통은 실패, 모름은 실패가 아니다.** 봉투가 `SUCCESS` 여도 센 통수가 0 이면 보낸 날을
   남기지 않는다. 다만 **통수 자리를 못 찾은 응답은 0통이 아니라 '모름'** 으로 본다.
6. **템플릿 코드가 없으면 로그 스텁으로 돈다.** 다만 코드는 있는데 인증서가 없으면 잡이 **실패한다.**
7. **한 통 보낼 때마다 커밋한다.** 묶어서 마지막에 한 번 커밋하지 않는다.
8. **조회에서도 익명키를 채운다.** 켜져 있는데 키가 없으면 그 자리에서 넣는다.

## 근거

- **`users` 가 아니라 `notification_settings` 인 이유.** 컬럼이 사는 곳이 곧 그 값의 수명을
  말한다. 설정 행 옆에 두면 "이 사람이 알림을 켜 둔 동안만 필요한 값" 이라는 게 스키마에서
  읽힌다. `users` 에 두면 지울 시점이 코드 어딘가에만 있고, 언젠가 지우는 걸 잊는다.
- **해시를 그대로 두는 이유.** 로그인·조회 경로는 여전히 해시로만 돈다. 원문이 새는 자리를
  알림 하나로 좁혔다. ADR-0003 을 뒤집는 게 아니라 예외를 하나 파고 그 크기를 못 박은 것이다.
- **재시도하지 않는 이유.** 알림은 못 간 것보다 두 번 울리는 쪽이 나쁘다. 응답을 못 받아도
  푸시는 이미 갔을 수 있고, 우리는 그것을 구분할 방법이 없다. 하루 한 번짜리 알림에서
  한 번 놓치는 비용은 작다.
- **0통을 실패로 보는 이유.** 동의를 안 한 사람에게 부르면 호출은 성공하고 발송만 0통이다.
  이것을 성공으로 세면 보낸 날이 남아, 그 사람은 영영 "보낸 것으로 처리된" 채로 아무것도 안 받는다.
- **코드가 없으면 스텁, 인증서가 없으면 실패인 이유.** 코드가 없는 것은 아직 콘솔 절차가 안 끝난
  정상 상태다. 코드가 있는데 인증서가 없는 것은 배포가 잘못된 것이다. 후자를 조용히 넘기면
  배포는 성공으로 보이고 알림만 안 간다.
- **건별로 커밋하는 이유.** 묶어서 마지막에 한 번 커밋하면, 50명 중 30명에게 보낸 뒤 잡이
  죽거나(OOM·SIGTERM) 커밋이 실패했을 때 그 30명이 전부 '안 보낸 것' 으로 남는다. 재시도가
  같은 분에 돌면 그 30명은 두 번 받는다. 커밋 한 번이 느는 값보다 두 번 울리는 값이 크다.
- **조회에서도 키를 채우는 이유.** 이 컬럼이 생기기 **전에** 알림을 켜 둔 사람은 값이 비어 있다.
  sha256 이라 backfill 이 불가능하고, PATCH 로만 채우면 설정 화면을 다시 만지지 않는 한 영영
  못 받는다. 화면에는 켜져 있다고 보이므로 사용자는 이유를 알 수 없다. 조회 요청에도 익명키가
  이미 실려 오므로 그 자리에서 채운다.
- **모름과 0통을 가르는 이유.** 응답 모양을 아직 실물로 본 적이 없다. 모르는 모양을 0통으로 세면
  정상으로 간 알림이 매번 실패로 기록되고, 진짜 미동의와 구분이 안 된다.
- **길이 상한을 안 두는 이유.** 토스 익명키의 최대 길이를 실측한 적이 없다. `VARCHAR(256)` 로
  잡았다가 넘치면 알림을 켜는 PATCH 자체가 500 이 된다. 이 크기에서 `Text` 는 값이 같다.

## 대안

- **익명키를 `users` 에 저장한다.** 버렸다. 위 근거. 지울 시점이 스키마에 안 드러난다.
- **저장하지 않고, 사용자가 앱을 열 때마다 그 요청으로 알림을 보낸다.** 버렸다. 알림의 목적이
  앱을 열게 하는 것인데 앱을 열어야 보내진다.
- **인앱 배너로 대신한다.** 버렸다. 사용자가 직접 거절했다: "이미 들어온 사람에게는 귀찮은
  버튼 클릭 한 번 더 늘어날 뿐이야."
- **`x-toss-user-key` 를 쓴다.** 버렸다. 토스 로그인 연동이 필요하고, 우리는 로그인 화면을
  만들지 않기로 했다(ADR-0003).
- **광고성 「재방문 유도」 캠페인으로 보낸다.** 버렸다. 사용자가 시각을 못 정하고(콘솔에서 일괄),
  발송 시작일 전 30일 사용자가 100명 이상이어야 한다. 아직 출시 전이다.
  다만 이 길은 **SDK 동의가 필요 없어 토스 5.255.0 미만에서도 닿는다.** 사용자가 100명을
  넘으면 다시 본다.

## 결과

무엇을 잃는가.

- **익명키 원문이 DB 에 생긴다.** 범위를 알림 켠 사람으로 좁혔지만 0 은 아니다. 이 값은 우리
  미니앱 전용 해시라 토스 계정을 가리키지는 않는다. 그래도 유출되면 그 사람에게 알림을 보낼 수 있다.
- **5.255.0 게이트는 그대로다.** 보내는 쪽을 뚫었을 뿐, 동의를 받는 `Notification.requestAgreement`
  는 여전히 안드로이드·iOS 5.255.0 이상이다. SDK 3.2.0 에 알림 API 는 이것 하나뿐이고,
  deprecated 된 옛 함수도 최소 버전이 같다. 우회로가 없다는 것을 확인했다.
- **문구 검수를 우리가 통제하지 못한다.** 「기록하러 오세요」가 리텐션 목적으로 읽히면 기능성이
  아니라 광고성으로 반려될 수 있다. 반려되면 위 「재방문 유도」 대안으로 내려간다.
- **한 사람씩 차례로 보낸다.** 같은 분에 몰린 사람이 많아지면 잡이 1분을 넘긴다. 사용자당 분당
  10회 한도가 있어 묶어 보내기도 마음대로는 안 된다. 규모가 커지면 그때 나눈다.
- **익명키가 만료·재발급되면 그 사람은 조용히 실패한다.** 다음에 앱을 열면 조회가 새 키로
  덮으므로 스스로 낫지만, 그 사이 며칠은 알림이 안 간다. 인증 실패를 보고 키를 즉시 비우는
  것까지는 안 했다.
- **아직 한 통도 안 보내 봤다.** 발송 코드가 없어 실기기 왕복을 못 했다. 검증한 것은
  MockTransport 로 만든 요청 모양과 실패 처리까지다.
